# 8. The AI handoff step

> Part of the [AI Dev Workflow Phase 1 design](README.md).

## Prompt composition

The composed prompt is assembled deterministically, always in this order:

1. **Template body**, then any **included templates** — each with placeholders resolved
2. **Workspace path map** — repo names mapped to absolute paths
3. **Scope constraint** — an instruction to work only within the listed folders
4. **Further reading** — `#file:` lines for the documents the template names, present only
   when it names any
5. **Output contract** — either an instruction to write the result to the declared output
   path, or, where the step produces edits, an instruction to change the code in place and
   write no summary file

Parts 2–5 are generated by the engine. Prompt authors write only part 1.

Within part 1 the step's own body comes first and included files follow, in the order they
are declared. Most specific at the top: a shared file is a constraint on the work, and reads
naturally after the work has been described.

Determinism is required: the same workflow, answers and extension version must produce a
byte-identical prompt. This is what makes the process standardised rather than merely
documented, and what makes the audit log meaningful.

The repositories in part 2 are not passed in. The handoff finds them itself, by walking back
through the steps before it for the most recent one that recorded repositories. A workflow
author never names them twice.

## Prompt template format

Plain markdown with `{{namespace.field}}` placeholders, stored in `prompts/` in the extension
repository and **found by convention** at `prompts/<workflowId>/<stepId>.md` — under the
team's content folder if they have supplied that template, otherwise under the extension's own
`prompts/` directory ([Section 16](16-external-content.md)). Nothing in the workflow JSON names
a template. This is why adding a workflow needs a JSON file and some markdown but no
TypeScript.

An optional YAML frontmatter block declares the artifact the model is contracted to write,
and the other markdown files the prompt leans on:

```markdown
---
output: 02-analysis.md
include:
  - _shared/house-rules.md
reference:
  - "{{task.workDir}}/party-service/docs/api.md"
---
You are helping a developer research an existing system before any code is written.
Platform: {{task.platform}}. Epic: {{task.epic}}.

## JIRA story, as written

{{requirement.story}}
```

## One handoff, several markdown files

A prompt is rarely only one file's worth of thinking. House rules apply to every coding step;
a team's Java conventions apply to every workflow; an OpenAPI document matters to one. Two
keys, because those are two different things to do with a file.

| Key | What happens | In the audit log |
|---|---|---|
| `include:` | The file's text is quoted into part 1 | The whole text, inside the prompt |
| `reference:` | The file's path is emitted as a `#file:` line in part 4 | The path, not the contents |

**`include:` is for wording you would otherwise repeat.** It is quoted, so it is visible in
the panel, byte-for-byte in the audit log, and determinism is untouched. It costs prompt
tokens on every handoff. Both bundled coding steps use it for
`_shared/house-rules.md`, which is what removed the duplication that used to sit at the
bottom of `CodeImplementation.md` and `CodeFix.md`.

**`reference:` is for documents too large to paste**, or that Copilot should consult rather
than read end to end. Placeholders resolve first, so a template can point at a document
inside a repository the task has just cloned — `{{task.workDir}}/party-service/docs/api.md`.
An absolute result is used as it stands; anything else is a name under the prompts root.

The accepted cost of `reference:` is stated plainly, because it is the one place the audit
log gets weaker: **it records what was pointed at, not what was said.** For `include:` the
log still answers "what was asked" completely. Prefer `include:` when the file is small
enough to quote.

### The rules that keep this from becoming a build system

- **Both keys live in the template's frontmatter**, beside `output:`. The reasoning is the one
  already given for `output:` — which other prompts a prompt leans on is the prompt author's
  decision, the same decision as what it asks for, and it belongs in the same file. Workflow
  JSON still names no template, so [D6](04-decisions.md) is untouched and adding a workflow
  is still JSON and markdown.
- **Names are relative to the prompts root**, not to the file declaring them. So
  `_shared/house-rules.md` means the same thing from every workflow. Absolute paths and `..`
  are refused: every quoted file must be either the team's or the bundled default, or the
  caption above the prompt and the audit entry stop meaning anything.
- **Each pulled-in file resolves with the same per-file fallback and the same case guard** as
  a step template ([Section 16](16-external-content.md)). A team may override
  `_shared/house-rules.md` alone and receive every other shared file a release adds.
- **Includes are one level deep.** An included file that declares `output:`, `include:` or
  `reference:` is an error naming the file. This is how cycles are prevented — by
  construction rather than by detection — and no bundled prompt has wanted more.
- **A missing `include:` is fatal; a missing `reference:` is not.** An include's text is part
  of what is being asked, and dropping it would change the prompt while the caption still
  claimed it was there. A reference is a pointer, and repositories differ: the `#file:` is
  emitted either way, and the panel names it as not found. What is sent is always what the
  panel shows.
- **A single name is accepted where a list would do.** `include: _shared/x.md` and
  `include:\n  - _shared/x.md` mean the same thing. One file is the common case and making it
  a list is the kind of ceremony that makes a format feel unfriendly.

The artifact name is frontmatter rather than code because which file a handoff produces is
the prompt author's decision — the same decision as what the prompt asks for, and it belongs
in the same file. A template with no `output:` declares a handoff that edits code; a step
whose completion depends on a file appearing ([D9](04-decisions.md)) cannot proceed without
one, and `invokeCopilot` fails loudly rather than inventing a filename.

The *content* of prompt templates is authored during implementation, not specified here. This
design fixes the template format, the placeholder namespace and the composition order; what
the prompts say is a matter for the developers who will tune them. These files are the
highest-leverage artifacts in the repository and are not code, which matters for a team of
Java developers. Senior developers tune them; the whole team receives the tuned version in
the next release.

## Placeholder namespaces

| Namespace | Resolves to |
|---|---|
| `{{task.platform}}` | Platform id selected at task start |
| `{{task.epic}}` | Epic key entered at task start |
| `{{task.dir}}` | Absolute path of the task folder |
| `{{task.id}}` | Task id |
| `{{task.<input>}}` | Any sidebar input: `services`, `baseBranch`, `workDir`, `taskType`, `featureStory` |
| `{{<stepId>.<fieldId>}}` | A field answer from any completed step |

**Task inputs.** Platform, epic, task type, base branch, work directory and microservices are
collected once in the sidebar before the workflow begins, stored on `TaskState.inputs`, and
exposed under the `task` namespace. No step re-asks for them. This keeps task-level facts out
of any single step's answers, so *any* workflow can reference them — and it is what makes the
sidebar and the workflow one system rather than two.

**An unresolved placeholder renders as empty.** The original design said referencing a step
that has not completed would be a load-time validation error raised by `WorkflowCatalog`. It
is not implemented: `resolveText` substitutes the empty string and composition continues. A
typo in a placeholder therefore produces a quietly incomplete prompt rather than a failure,
and the only thing that catches it is a test asserting the composed text, or a developer
reading the prompt in the panel before sending it. That is the strongest argument for showing
the composed prompt rather than hiding it.

## Pointing Copilot at code

The engine emits `#file:` references for the selected repositories so the model is directed
at real paths rather than told about them in prose.

The scope constraint is stated but **not enforced** — Copilot can read and edit anything in
the workspace. This is inherent to [D1](04-decisions.md), and is the reason the generated
workspace contains only the repos the task needs.

## The prompt is shown, and can be edited

Every handoff step renders its fully composed prompt in the panel, in a box the developer can
type into, with Copy, Send to Copilot and — once there is an edit to undo — Reset. Above it,
a caption names every file that shaped it: the template, one line for the files it included
with the origin of each, and one line for the files it referenced, marking any that are not
on disk. That last is the only place the discrepancy can be seen, since the `#file:` is in
the prompt regardless.

Showing it is what makes [D1](04-decisions.md) tolerable: the developer can see exactly what
is being asked on their behalf before it leaves. Letting them change it accepts that a
composed prompt is sometimes wrong for the task in front of them, and that pasting a
corrected version into the chat by hand is what happens anyway when it is.

The edit is written into the step's `answers` when Copy or Send is pressed, so it survives a
reload. Typing and then closing the panel without pressing anything loses it; persisting
every keystroke would cost a round trip per character.

**The audit log records the prompt that was sent, not the one that was generated.** There is
deliberately no separate record of the fact that an edit occurred. The log therefore still
answers "what was asked", which is the question it exists for, and no longer independently
corroborates what the extension composed.

Composition failure is returned rather than thrown. The descriptor describes every step, not
only the active one, so a broken template shows its error on the step that owns it instead of
taking down the whole panel.

## Handoff mechanism and fallbacks

| | Mechanism | Developer experience |
|---|---|---|
| A | `executeCommand('workbench.action.chat.open', { query, mode: 'agent' })` | One click; prompt prefilled |
| B | Copy prompt to clipboard, then open chat | One paste |
| C | Write `.engine/prompt.md` and open it in an editor tab | Copy from the editor |

All three are functional: the value lies in the composed prompt, not in how it reaches the
chat box. The step degrades from A to B to C inside `ChatHandoff` and nowhere else. Which
mechanism succeeded is recorded on the step result and in the audit log.

## Completion detection

For a handoff contracted to write a file, both conditions are required ([D9](04-decisions.md)):

1. A file watcher observes the declared output file appear or change, **and**
2. The developer confirms.

If the developer confirms and the file is absent, the step reports the missing output and
does not advance. Repeated misses on the same step are the signal that a prompt template
needs revision.

**For a handoff that produces edits, only the second condition exists.** `invokeCopilotCoding`
and `invokeCopilotCodeReview` change repositories rather than writing a document, so there is
nothing to watch for and completion rests on the developer's word. This is the one place D9
gives, and it gives because the alternative — inventing a summary file to watch for — would
put a false promise in the audit log.

## Audit coverage

**Captured:** workflow id and version, every developer input, every action the panel sent,
the exact prompt as delivered, the handoff mechanism used, timestamps, the reviewed
artifact's path and content hash, every approval and every revise loop, any detected
tampering with the workflow snapshot, and — for each handoff — the path of the template the
prompt was composed from, the path and origin of every file it included, the path of every
file it referenced, and whether each of those was the team's or the bundled default.

**Not captured:** anything inside Copilot Chat — follow-up turns, or unrelated conversation.
**Nor the contents of a referenced file**, only its path — see the cost noted above.
**Nor a copy of the artifact.** The original design said the returned artifact was stored
alongside its hash; only the hash is recorded. The hash proves the file was not altered after
approval, but it cannot reconstruct what was approved if the file is later edited or deleted,
and the artifact lives in a folder the developer is invited to edit. Storing a copy at
approval time is a small change and would close that gap.

This gap is the accepted cost of [D1](04-decisions.md). Input, output and approvals still
cover the question the tool exists to answer.

## Known friction

Agent mode must be enabled in the developer's Copilot settings, and it requests confirmation
before editing files or running commands. The extension cannot suppress either.

The original design said P1 would check the setting at task start and report it up front
rather than letting the developer discover it mid-workflow. **That check is not implemented.**
Mechanism A requests agent mode in its arguments, and if the request is not honoured the
handoff still appears to succeed — the developer finds out when Copilot answers in chat
instead of editing files.
